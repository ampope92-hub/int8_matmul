We're moving a dense layer onto an int8 path and the kernel has to be hand written in Rust. The box is offline, there's no BLAS, and the dependency list in /app/kernel/Cargo.toml is empty on purpose. /app/data/weights.bin is the weight matrix, 512 by 192 little-endian f32, row-major, no header; /app/data/activations.bin is a capture of activations at that layer, 96 by 512, same encoding. /app/data/README.md has the provenance; leave both binaries as we shipped them. Fill in /app/kernel/src/main.rs so it takes one argument and handles both of the steps below. Run one is cargo run --release -- calibrate from /app/kernel with /app/out empty. It reads both tensors and writes six files into /app/out:

- output.bin, the dequantized product for that capture, 96 by 192 little-endian f32, row-major
- weights_q.bin, the quantized weights, 512 by 192, one signed byte per entry, row-major
- w_scales.bin, 192 little-endian f32, one per output column
- acts_q.bin, the quantized activations, 96 by 512, one signed byte per entry, row-major
- a_scales.bin, 96 little-endian f32, one per activation row
- params.bin, anything else your calibration settled that the serving step needs, as little-endian f32, at most 512 of them. It can be empty if you don't need it.

Run two, cargo run --release -- apply, is the serving step and it is the one we score. We keep params.bin exactly as calibrate wrote it and hand it back read-only in /app/scheme. The weight side does not come with it. There are no weights on the box at all during this step, in float or in int8, because the server already holds what your calibration run committed and does the product itself. /app/data then holds one file, activations.bin, a fresh capture at the same layer that was not on the box when you calibrated, and the capture you did calibrate on is gone too. From that, write acts_q.bin and a_scales.bin into /app/out in the same formats as above. Whatever you decided about the weights is already fixed by then, so the serving step lives with it.

Two things have to hold. On the calibration run output.bin has to agree with the integer product of the tensors it handed back, a_scales[m] * w_scales[n] * sum over k of acts_q[m,k] * weights_q[k,n], to a relative 1e-4. It also has to be a real product of the capture you were given. We work out the exact product of the two tensors ourselves and the worst column of output.bin has to come within 20 dB of it. Zeros agree with zeros, and that is not a quantization. And accuracy is scored on the serving runs, column by column. We take the codes a serving run wrote, put them beside the weights_q.bin and w_scales.bin your calibration run committed, form that same product, and compare it against the full precision answer in double precision: SQNR_n = 10 * log10( sum over m of ref[m,n]^2 / sum over m of (out[m,n] - ref[m,n])^2 ). The lowest SQNR_n across all 192 columns has to reach 29 dB. The worst column, not the average, thats the one that shows up downstream. We put the same kernel through the same two steps on another export of this layer, a different draw of both tensors, and there it has to reach 28 dB. So it has to work from whatever is sitting in /app/data when it runs, and numbers worked out once and written into the source as constants are no use to us. Keep Cargo.toml and Cargo.lock buildable, we rebuild from the sources we collect. Keep everything you write under /app/kernel/src, because that and the two Cargo files are all we take, with no build script, nothing under src but .rs source files, and every dependency table empty. We check the manifest and the files for that. While your binary runs, no compiler, interpreter or shell on the box can be executed by it.
